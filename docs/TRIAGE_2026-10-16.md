## #4 — BLE upload failure triggers a retry loop the uploader explicitly forbids

**Landed:** PR #13 (`fix/a-retry-recovery`): `a21fcd1` classify failures by CONTROL2,
`e45e0b9` shared supervisor helpers, `5336c78` no restart after an interrupted transfer,
`71ca4f4` START_STACK clears the halt, `8559eb3` STATUS shows the halt, `367e21f` policy doc.
PR #16 (`fix/device-selection`): `dc30996` codes 10/11 retry every 5 min and never halt,
`583faf9` and `60e94c1` the halt instruction (no power switch; disconnect the battery ≥ 30 s).

**Hardware:** verified. Real code-20 halts at 21:05, 21:39, 22:44, 22:46 and 23:00 on
2026-10-15 and 18:50 on 2026-10-16, each held until START_STACK after a battery
disconnect, with the renderer still running. Code-10 retries without a halt after a
restart: four times (21:35, 23:09, 23:15 on 10-15; 18:49 on 10-16). **Not verified:** the
killed-process / session-marker path (an uploader killed mid-transfer).

**Proposed: close** when v0.3.0-beta.1 is released (your earlier comment said "leaving
open until release"). The marker path is covered offline (`tests\test_supervisor_retry.ps1`,
"killed (code 1) with marker"). It doesn't need its own issue unless you want one.

> Fixed on `main` (#13, #16) and verified on hardware: six real interrupted transfers
> (2026-10-15 21:05, 21:39, 22:44, 22:46, 23:00; 2026-10-16 18:50) each halted, were not
> retried, kept the renderer running and recovered via `START_STACK` after a battery
> disconnect. Codes 10 and 11 now retry every 5 minutes instead of halting; that path
> recovered on its own after four restarts. The killed-process / session-marker path is
> tested offline only. Details: `docs/PROJECT_HISTORY.md` §7.1. Closing with the
> v0.3.0-beta.1 release.

## #5 — Display stays on standby if media was already playing when the renderer starts

**Landed:** PR #12: `13c218c` release standby for steady playback with a frozen timeline
(the 15-second rule). Offline tests in `tests\test_renderer.py`.

**Hardware:** not verified. On 2026-10-15 a restart with Spotify already playing released
standby in 2 s through the *old* "timeline advancing" path; the new rule never fired. The
bug was only ever reproduced synthetically, and no real provider is known to report a
frozen timeline.

**Proposed: close**, with "reopen if seen". Waiting for a provider that may not exist
keeps it open indefinitely. *Alternative if you prefer:* keep it open, labelled
"needs field report". That's your call; I have not changed any label.

> Fixed in code on `main` (`13c218c`, #12): steady playback with valid metadata now
> releases standby after 15 s even if the reported timeline never moves. Covered by
> offline tests. Not seen on hardware: on 2026-10-15 Spotify released standby through the
> normal "timeline advancing" path within 2 s, and no real provider is known to report a
> frozen timeline. Closing; please reopen with your player's name if the display stays on
> standby while music is playing.

## #14 — Uploader picks the wrong BLE device when two advertise a matching name

**Landed:** PR #16: `5223945` select by media service, not name; `ca51d3a` rescan once
when every candidate is rejected, log what a rejected device exposes; `dc30996` code 11
retries; `cc07788` rank by name (cached → exactly `Zoom75 Tiga` → other → `… BT<n>` last);
`4e5b2ac` keep scanning up to 15 s while nothing is seen.

**Hardware:** verified on 2026-10-15: BT1 identified (`Zoom75 Tiga BT1`), rejected after
a failed connect (23:06), address cache (23:09). On 2026-10-16 the live install (with
`cc07788` and `4e5b2ac`) selected `Zoom75 Tiga` from the cache at 17:52, 18:49 and 18:54,
and logged `Nothing seen in 5 s; scanning up to 15 s` at 18:48:50. Every upload in both
installs' logs since the fix went to the correct device. **Not verified:** a cold start with no `.device` file
(the name ranking on its own), and what BT1 exposes (its connect failed, so no `exposes`
line yet).

**Proposed: close.** Your comment said "leaving this open until the branch is merged",
and #16 is merged.

> Fixed on `main` (#16) and verified on hardware: a device now qualifies only if it
> exposes the media service and its four characteristics. `Zoom75 Tiga BT1` (the
> keyboard's Bluetooth typing connection) was rejected and the display device selected,
> and the last working address is tried first on the next start. Since the merge, every
> upload on 2026-10-15/16 went to the correct device. Not yet seen on hardware: a cold
> start with no cached address (covered by offline tests). Closing.

## #15 — Display control reports a command as sent when the write never reached the renderer

**Landed:** PR #16: `dbc902f` read back after writing, wait up to 10 s for the renderer's
ack, report plainly when it doesn't arrive; `f124932` no shutdown offer without the
renderer's ack.

**Hardware:** verified on 2026-10-16, 20:54–20:56 (PROJECT_HISTORY §7.1, fourth part).
Three commands from Display Control: Lock Standby, Lock Standby again, Resume Automatic.
The renderer acted on each within a second (`CONTROL -> manual standby` twice, then
`CONTROL -> automatic mode re-armed`), wrote its ack (the surviving one matches the third
command, 0.9 s after the command file), and each frame was uploaded (11.38 s, 10.68 s,
9.97 s). **Not covered:** a write that really fails (the error path); the original cause
(antivirus sandboxing a freshly built exe) is still a theory. In the same session a
freshly rebuilt uploader took ~25 s to start on its first run, which fits that theory.

**Proposed: close.** The issue is "reports a command as sent when it never arrived". The
utility now confirms arrival, and that confirmation worked on hardware. The error path
is covered by the code and the docs; it can't be induced on demand. Standby + Shut Down
stays with #7.

> Fixed on `main` (`dbc902f`, `f124932`, #16) and verified on hardware on 2026-10-16:
> Lock Standby, Lock Standby again and Resume Automatic were each confirmed by the
> renderer's acknowledgement and uploaded to the keyboard. The utility now reads every
> command back and waits for the renderer's acknowledgement before reporting success,
> and says plainly (with the path and antivirus as a possible cause) when either fails.
> Standby + Shut Down's delivery check is tracked in #7. Closing.
